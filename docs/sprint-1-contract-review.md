## Task 1 contract and security design

1. Fetch `GET /auth/csrf-token`; keep returned token in memory, retain signed HttpOnly `_csrf` cookie, send `x-csrf-token` on **every unsafe method**, including unauthenticated auth operations. Missing/mismatch is 403. SameSite is additional protection, not a CSRF substitute. Use exact-origin same-origin deployment; no credentialed wildcard CORS. No new bearer-token issuance path proposed.
2. Student registers at `POST /auth/register`: normalized unique email, strong password and names; server assigns student role and creates minimal student profile in one transaction. Return 201 identity ID plus verification challenge, **without login cookies**. Duplicate is 409. Unknown fields, especially role/permissions, are 422. Guardian consent cannot be inferred from this schema; eligibility is decision-gated.
3. Email verification uses request/resend and OTP verify endpoints. A verification request returns uniform 202 with an opaque challenge even for unknown/ineligible addresses. Successful verification is 200/null; login is separate. Six digits, ten minutes, five wrong attempts, 60-second resend cooldown, five hourly sends per normalized address plus IP limits are **proposed values**. Exhaustion returns 429 with Retry-After. Invalid/expired/consumed credentials return generic 422. Store hashes/HMACs of short OTPs with server-held secret, purpose, attempt count and expiry. No raw credentials in DB/logs/docs. Store keyed address throttle identifiers and preserve counters across resend; creating decoy challenges must not allow bypass or unbounded storage.
4. Login routes are `/auth/student/login`, `/auth/faculty/login`, `/auth/admin/login`; email/password plus exact current portal role required. Wrong portal and invalid/inactive/locked identity return generic 401. Verified password but unverified email returns 403. No role selector that grants roles. Proposal: one portal role per identity in Phase 1, global unique email; duplicate cross-role email returns 409. Multi-role identities need explicit design review if required.
5. Reuse JWT cookie transport. Proposed 15-minute access TTL and seven-day **absolute**, non-sliding session lifetime. `accessToken`: HttpOnly, Path=/; `refreshToken`: HttpOnly, Path=/api/v1/auth; host-only, SameSite=Strict, Secure on deployed HTTPS. Local HTTP may omit Secure. Cookie Max-Age must derive from actual remaining validity; eliminate controller's hardcoded refresh-age mismatch. Pin accepted algorithms (HS256 with existing frontend), validate issuer/audience/purpose/claim shape and use distinct signing keys. Never expose access/refresh tokens in JSON or browser storage. A user can log into another portal only by obtaining a new role-checked session; one cookie pair means switching sessions, not simultaneous independent portal logins.
6. Add stable server session-family ID linking access and rotating refresh credentials; keep hashes and rotation ancestry. Every protected API checks authoritative live account/role/session state in PostgreSQL. Redis may accelerate or rate-limit but must not make revocation optional. Replayed refresh credential revokes family including access credentials; rotation is atomic. A consumed refresh yields 401; session absolute expiry requires login. Fail closed 503 if required authoritative checks are unavailable. No application permissions granted merely from stale claims. Frontend middleware remains a navigation hint and may briefly display a stale shell; backend data endpoints remain authoritative.
7. Logout revokes current family immediately and clears both cookies with exact paths; remains idempotent without a valid session, but requires CSRF. Logout must process a present refresh credential even if access is expired. Self revocation never accepts another owner's session; 404 conceals it. Revoking other sessions retains caller identified by access session, not an arbitrary submitted refresh token. Session management shows no tokens or fingerprints. Login/refresh clients serialize rotation, retry protected calls only once, and never blindly retry credential submissions.
8. Recovery uses email + portal, uniform request response, OTP verification, then short-lived one-use reset credential returned only after successful OTP verification. Proposed reset grant TTL five minutes. New request invalidates previous OTP and reset grant; attempts aggregate, grant consumption is atomic, reset to current password is rejected. Reset revokes all sessions and outstanding auth challenges, clears cookies, audits action and requires fresh login. It does not silently verify an unverified email. Do not add an OTP-read API; tests capture mail through an injected test adapter.
9. `POST /auth/reauthenticate` verifies current password and records proposed five-minute freshness in the current session; no reusable proof bearer token. Sensitive admin operations and verification-file retrieval require freshness; expired freshness is 403. Password change requires current password and revokes all sessions. Reauthentication does not extend absolute expiry or upgrade role.
10. Admin-created faculty receives activation/recovery email without admin-selected or emailed password. Faculty credential record is pending activation until a secure password is set; email verification remains required before login. Login before faculty approval permits onboarding, not student operations. Before terms acceptance/password activation, allow only me, own profile/document metadata reads, terms read/accept when activated, and identity/session maintenance. No catalogue mutation, publishing or discovery eligibility from login alone.
11. Initial admin: proposed operator-only command, explicit intended database verification, secure interactive secret input or secret-manager delivery, transactionally assign admin, record provisioning audit, verify email, no hardcoded/seeded password. Refuse accidental second initial-admin creation. Do not add HTTP provisioning or public admin registration. Command details implemented only after approval.
12. Record domain audit events for registration, OTP request/verification/failure (without OTP), login success/failure, refresh replay, logout/revocation, reauthentication, password change/reset and activation, faculty transitions, catalogue/pricing/library/settings writes, document access and audit reads. Include UTC action timestamp and actor where identifiable; unauthenticated failures have null actor when unknown. Existing role changes, if retained, must audit before/after role IDs and immediately revoke sessions. No generic role-management endpoints are approved here. Security event persistence must be explicit, not inferred from HTTP-request logging; state changes and their audit/outbox records should commit atomically.

## Faculty lifecycle and shared eligibility

Admin create → credential activation + email verification → faculty login/terms acceptance → admin setup/evidence/catalogue assignments → admin approval → explicit publication. Rejection returns profile to non-visible state. Re-review follows corrections. Proposed material profile/evidence edits reset approval to pending and unpublish. Review and lifecycle operations use expectedRevision to reject stale decisions. Approval must refer to a committed revision.

`visible = user.active && user.emailVerified && faculty.active && terms.currentAccepted && approval==approved && published && hasActiveValidAssignment`.

This is also the shared **prerequisite** for future bookability. It does not implement booking requests, availability, slot locks, charging, attendance or payouts. A selected offering additionally requires active catalogue chain/assignment and configured price; later booking checks will be added in Sprint 2. Do not conflate public visibility with price availability: an eligible published tutor may have no configured price, yielding explicit unavailable.

Status changes re-evaluate live on every consumer read. Deactivation also disables identity access, revokes sessions and unpublishes. Reactivation preserves prior terms/approval but does not auto-publish. Proposed new required terms version immediately makes current acceptance false; whether reapproval is needed remains undecided. Public projections exclude email, private identity flags, verification files and moderation notes. Private document ownership is checked through faculty/user relationships on every byte retrieval, including nested document IDs. Admin and owning faculty can retrieve only clean files with recent reauthentication. Admin-only verification upload is the current Task 2 proposal; no faculty-upload assumption.

## Catalogue, pricing, library and settings

Catalogue uses separate configurable Category, Board, Subject, Level and Curriculum records. Curriculum is a valid category/board/subject/level tuple with syllabus text. A School tuple requires a board, non-School requires null. Board is null-equal in uniqueness constraints; no nullable-unique loophole. Board/subject/level master rows become applicable to a category only through valid configured curricula. Seed four category labels exactly as requested; a combined Research & Skill Learning category remains one row. State boards are admin-entered named structures, not an invented exhaustive list. If multiple syllabi for the same tuple are required, extend the tuple explicitly before implementation.

Assignment is unique faculty+curriculum. One price per assignment, integer paise, INR, fixed 60 minutes. Board cannot be silently ignored when distinguishing School offerings. An inactive row is reactivated, not duplicated; references must be valid. `GET /prices/resolve?facultyId=…&curriculumId=…` returns either available=true/price or available=false/reason, including NO_CONFIGURED_PRICE; it never invents a default. Admin archive is `isActive=false`; no cascading delete API. Reparenting an in-use curriculum is rejected; archive/create instead. Prices do not model package combinations, bundles, credits or subscription periods.

Library proposal is deliberately marked decision-required: **admin-only submissions, admin moderation, authenticated-student audience**, no faculty submission path. It is not claimed as the agreed permission policy. Initial proposed files PDF/JPEG/PNG ≤10 MiB; broader permitted formats must be approved. Files are private/quarantined, scanned, then moderated; clean scan does not equal approved. Metadata and bytes/link retrieval enforce the same current audience/moderation/catalogue rules. Moderator can inspect clean pending files; students receive 404 for hidden resources. No public URLs or storage keys. Link retrieval returns an authorized HTTPS destination, not an arbitrary proxy. External content is not controlled after the user visits it; approval cannot guarantee destination contents stay unchanged. Proposed distinct moderator/uploader prevents self-approval and needs review. No edit endpoint after approval: submit replacement and withdraw old record through moderation, preserving history.

Settings are a typed server-owned registry of non-secret keys with bounds/enum, value, revision and audit. Admin can change values without deployment, not invent executable definitions, write secrets or alter types. Wrong runtime type/range is 422; stale revision 409. Apply and invalidate caches before acknowledging success. Business rates are Price records, not redundant settings. Proposed initial definitions for review: `security.otpTtlSeconds` integer 60–1800 (600 proposed), `security.otpMaxAttempts` integer 1–10 (5), `security.otpResendCooldownSeconds` integer 30–600 (60), `security.otpMaxSendsPerHour` integer 1–10 (5), `security.reauthenticationTtlSeconds` integer 60–600 (300). Enforce resend cooldown < OTP TTL. OTP policy snapshots attach to each challenge; tightening global throttles must not reset existing counters. Accepted terms are immutable reviewed documents, not editable arbitrary settings. No future scoring/payment engine or unapproved scoring default.

Audit access reuses `/audit` and `audit.read`, with admin role required. Read-only redacted list, filters and stable pagination; no hash-chain secrets or raw authentication material exposed. Existing audit-detail endpoint is not needed for this draft; a future decision may retain it with the same redaction/access policy. New allowlisted security metadata must be distinguishable from PII.
